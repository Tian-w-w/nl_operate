# v0.5：知识问答、多轮查询与城市去重统计

本轮沿用现有订单服务和受限 Agent 循环，增加知识检索及引用、服务端会话记忆、查询条件修订和城市去重计数。默认使用用户确认的演示知识，正式模型效果仍需在实际网关环境验证。

## 使用与更新

在项目根目录停止旧服务后执行：

```powershell
git pull --ff-only
npm run build --prefix frontend
.\.venv\Scripts\python.exe -m scripts.manage dev
```

无需安装新 Python / npm 依赖，也没有新增数据库迁移；会话内容复用已有 Plan JSON 和结果集。保留已有 `.env`、数据库及模型配置。浏览器使用 Ctrl+F5 更新资源。

## 知识问答

在助手中可以询问：

```text
规定的发货时间是多少？
默认发什么快递？
公司的退货政策是什么？
```

前两项命中内置演示资料，最后一项目前没有资料，应明确回答缺少依据。侧栏新增“知识库”入口，可查看当前身份可访问的资料；回答下方可以展开引用原文、演示标记和内容版本。

内置普通现货48小时发货、默认顺丰速运仅为演示规则，不是公司正式规定，也不会修改合成订单的承运商。运费、包邮和承诺到货时间没有提供确定规则，不能据此生成价格或时效承诺。

真实模型模式的流程为：按当前租户过滤资料 → Markdown 按二级标题分段 → 中文双字词及同义词扩展的 BM25 检索 → 将最多3段资料与会话上下文发送给模型 → 校验回答引用 → 展示答案和原文。没有额外的 embedding 服务或向量数据库依赖。这是轻量词法检索，不声称具有向量语义检索的召回能力。

单步模式使用原有 `propose_action` 请求中的知识上下文生成答案；Agent 模式使用结构化 `answer_knowledge` 决策，知识问题不调用订单查询工具。离线规则模式只摘录检索原文，界面明确标注“知识库检索原文”，不冒充模型生成。无资料时服务端覆盖模型的任意猜测；有资料时必须引用本次检索的合法来源，伪造来源会停止任务。引用校验不能替代对模型回答事实一致性的人工或真实模型评测。

### 替换为正式资料

编辑 `data/knowledge/shipping.md`、`delivery.md`，或者添加新的 Markdown 文件并登记到 `data/knowledge/manifest.json`。每个可检索片段以 `## 标题` 开始。清单示例：

```json
{
  "documents": [
    {"id":"shipping-policy","file":"shipping.md","title":"已确认的发货规则","tenants":["a"],"is_demo":false}
  ]
}
```

先替换并审核内容，再设置 `is_demo=false`。`tenants` 是允许访问的服务端租户白名单；模型不能选择租户或任意文件。文件路径必须位于知识目录内。最多64份文档，每份不超过100KB，总片段不超过256；每片段最多700字。版本由文件内容 SHA-256 摘要生成，已保存回答保留当时的引用原文和版本。文档修改后下一次检索直接读取新内容。

## 多轮查询

先输入：

```text
查询上海等待发货超过48小时的订单，按金额降序，只展示列表和数量，不要导出。
```

再输入：

```text
把已发货的也一并查出来
```

第二轮保留上海、金额条件和原排序，结果含“上海超48小时待发货”与“上海已发货”两部分。已发货分支不再受“等待发货”条件约束，也不会把北京等其他城市带进来。继续说“那只看已发货的”，则仅替换状态，并移除不再适用的等待时限。

技术上保存最近任务原文、真实终态和结果摘要，模型每轮读取最近6轮摘要及服务端当前查询；当前查询优先于历史文字。页面刷新后通过 `/api/conversation` 恢复最近12轮对话。同一登录会话可跨刷新继续，切换身份或新会话不会继承旧会话内容；这是当前会话的记忆，不是跨用户长期记忆。

查询分为全新查询（new）、继续缩小（refine）和修订部分条件（revise）。refine 保留原集合交集；revise 合并未提及的条件并允许显式清除条件；“也加上某状态”使用独立的追加状态分支。明确的追加状态句式由服务端保护原城市、金额和排序，避免模型漏传条件造成范围扩大。结果集已过期或没有可用查询时停止并要求先查询，不退回全租户查询。追加查询未要求导出时，不沿用历史导出操作授权。

离线规则只覆盖明确句式；复杂省略、多条件替换、指代仍取决于模型理解，不能声称任意多轮表达都已支持。

## 城市去重计数

```text
统计一下一共有多少个收货城市
统计一下一共有多少个收获城市
这些订单有几个收货城市
```

前两句默认统计当前租户符合条件的全部订单中的不同城市，“收获城市”按常见笔误解释为“收货城市”；第三句统计当前完整结果集。回答明确显示统计范围、不同城市数、涉及订单数，并可展开各城市订单数。

新增只读工具 `count_order_values` 使用实际数据库分组计数，不把当前页行数当城市数，不为了统计而重置列表、结果集或页面版本。当前字段仅支持 `shipping_city`。模型将明确城市计数误判为普通查询时，服务端会约束到城市去重统计；任务轨迹保留原模型提议与实际执行决策，不能把这种服务端纠正算作模型独立理解成功。Agent 必须引用真实统计观察的 `statistic_id`，服务端生成数量反馈，不能由模型编造统计值。

## 检查与边界

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_conversation_knowledge.py
.\.venv\Scripts\python.exe -m scripts.manage test
```

前端现有浏览器流程新增多轮追加及刷新恢复、城市数量与页面保持、知识引用与未命中三条场景。原查询/导出 Agent 的24条脚本回归继续保留；它不是这批新知识问答的真实模型评测成绩。

模型调用仍在数据库事务外执行，返回后检查会话、页面版本、截止时间和来源依据。保留模型调用、工具调用、重复调用及总时限。当前模型接入支持完整自定义 URL，但公司网关的实际兼容性、限流及知识回答准确率需要在用户环境联调，未在本机进行真实模型调用。
